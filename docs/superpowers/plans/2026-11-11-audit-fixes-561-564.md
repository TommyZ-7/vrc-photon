### #542 の事前調査結果

- システムの `sqlite3` 3.54.0 では、`CREATE TABLE ... GENERATED ALWAYS AS (strftime(...)) STORED` は成功した。
- ただし `ALTER TABLE ... ADD COLUMN ... STORED` は `cannot add a STORED column` で失敗する。
- したがって **v18 は photos テーブルの再構築**で生成列を追加する。新規 DB は `SCHEMA_V1` に生成列を含めて作成し、v18 は既存 DB だけ再構築する。
- bundled SQLite（`libsqlite3-sys` 0.39.1）での `strftime` 生成列は Task 8 の最初のテストで確認する。失敗したら実装を止めて報告する。

## Review Focus

1. **#542 の photos 再構築**: 既存行、子テーブルの外部キー、索引、`AUTOINCREMENT` の採番がすべて保持されること。子行を持つ v17 DB からの移行テストと `PRAGMA foreign_key_check` で固定する。
2. **#561 の poison 回復**: panic したワーカーが保持していた Mutex を回復しても、値の不整合やデッドロックを起こさないこと。panic → 別ワーカーが同じ Mutex を取得して処理を続けるテストで固定する。
3. **#555 / #557 のロック外 I/O**: XMP 読み取り・サムネイル削除の間に DB ロックを保持しないこと。バリアで I/O を止め、別スレッドが `try_lock` できるテストで固定する。
4. **#560 のチャンク失敗時**: チャンクのトランザクションが失敗しても写真を取りこぼさず、どの写真が失敗したかを従来どおり報告すること。1 件ずつフォールバックするテストで固定する。
5. **#558 の見積もり不足**: AVIF/JXL の圧縮ファイルサイズと EXIF 回転のコピーを予算に含め、実測ピークを下回らないこと。回転あり・AVIF の見積もりテストで固定する。
6. **#546 のトースト連発**: ライブラリ再読込のたびにトーストを出さず、切り詰め状態になった最初の 1 回だけ出すこと。状態遷移のテストで固定する。

  ```rust
  pub(crate) fn lock_unpoisoned<T>(mutex: &Mutex<T>, label: &'static str) -> MutexGuard<'_, T>;
  ```
- `lock_unpoisoned` は poison を `PoisonError::into_inner()` で回復し、`tracing::error!(mutex = label, "recovered poisoned mutex")` を出す。

- [x] **Step 1: 失敗するテストを書く**

`lock.rs` に以下を追加する。

```rust
#[test]
fn poisoned_db_lock_recovers_and_keeps_workers_running() {
    let db = Arc::new(Mutex::new(Db::open_in_memory().unwrap()));
    let poisoned = Arc::clone(&db);
    let _ = std::panic::catch_unwind(AssertUnwindSafe(|| {
        let _guard = poisoned.lock().unwrap();
        panic!("worker panic while holding the db lock");
    }));
    assert!(db.is_poisoned());
    let guard = lock_db(&db);
    assert!(guard.count_photos().is_ok());
}

#[test]
fn poisoned_status_lock_recovers() {
    let status = Arc::new(Mutex::new(DaemonStatus::default()));
    let poisoned = Arc::clone(&status);
    let _ = std::panic::catch_unwind(AssertUnwindSafe(|| {
        let _guard = poisoned.lock().unwrap();
        panic!("worker panic while holding the status lock");
    }));
    let mut guard = lock_status(&status);
    guard.worker_restarts += 1;
    assert_eq!(guard.worker_restarts, 1);
}
```

- [x] **Step 4: デーモン内の DB / status ロックを置き換える**

- `ipc_server.rs` の `unwrap_or_else(|poisoned| poisoned.into_inner())` は `lock_db` に統一する

## Task 13: #564 revision bump など静かなエラー握りつぶしを解消する

**Files:**

**Interfaces:**
- Produces:

  ```rust
      destination: &Path,
      bytes: &[u8],
  ) -> io::Result<PlaceOutcome>;
  ```

- `write_bytes_no_clobber_durable` は `write_all` → `flush` → `sync_all` → `place_no_clobber` → 親ディレクトリの `sync_all`（Unix のみ、失敗は warn）を行う。

- `hash_loop` は `revision_pending` フラグを持ち、ハッシュ保存後または前回失敗時に `retry_revision` を呼ぶ。失敗は `tracing::warn!` で記録し、次の 2 秒周期で再試行する。
- ベストエフォート箇所（一時ファイル削除、thumbnail stamp 失敗）には「best effort」のコメントを付ける。

```rust
#[test]
fn durable_write_keeps_no_clobber_semantics() {
    // 新規 destination に durable 書き込み → Placed、bytes 一致。
    // 既存 destination に durable 書き込み → DestinationExists、既存 bytes 不変。
}
```

`lib.rs`:

```rust
#[test]
fn revision_bump_retries_after_a_failure() {
    let mut pending = true;
    let mut calls = 0;
    let first = retry_revision(&mut pending, || {
        calls += 1;
        Err(anyhow::anyhow!("database busy"))
    });
    assert!(!first);
    assert!(pending);
    let second = retry_revision(&mut pending, || {
        calls += 1;
        Ok(())
    });
    assert!(second);
    assert!(!pending);
    assert_eq!(calls, 2);
}
```
